#+title: Rewriting git history: folding changes into the root commit

Notes taken while folding a working-tree change set into the first commit of
=EngineeringSoftware/excoder=, [2026-09-01 Tue].

* Goal

Make an existing working-tree change set appear as though it had always been
part of an earlier commit, rather than landing as a follow-up commit.

* Procedure

Two passes: one to fold the content in, one to normalise the timestamps.

** Pass 1 --- fold the change set into the root commit

#+begin_src sh
git tag backup-pre-rewrite dda0d4b
git add -A
git commit --fixup=5097893
GIT_EDITOR=true GIT_SEQUENCE_EDITOR=true git rebase --autosquash --root
#+end_src

** Pass 2 --- align committer dates with author dates

#+begin_src sh
git tag backup-pre-datefix HEAD
GIT_EDITOR=true git rebase --root --committer-date-is-author-date
#+end_src

* Mechanism

** git add -A and rename detection

Staging deletions and their untracked replacements /together/ lets git pair them
by content and record renames rather than delete-plus-add. A rename reports zero
changed lines; a delete-plus-add reports the full file twice.

** --fixup and --autosquash

=--fixup=<sha>= writes an ordinary commit whose message is the literal string
=fixup! <subject-of-target>=. =--autosquash= makes rebase scan the todo list for
that prefix, reorder the commit to sit immediately after the target it names,
and change its action from =pick= to =fixup=.

The =fixup= action merges the diff into the target and discards the fixup
commit's own message. The target's message is left untouched, so the absorbed
commit leaves no trace.

** --root

Rebase normally replays commits onto a base and cannot touch the first commit,
which has no parent to rebase onto. =--root= rewrites from the first commit
onward, making it a valid fixup target.

** Editor suppression

Autosquash opens the todo list for confirmation. =true= is the no-op command
that exits 0 immediately; git reads that as "editor closed cleanly, file
unmodified" and proceeds with the generated plan. Required in non-interactive
environments.

- =GIT_SEQUENCE_EDITOR= :: the rebase todo list
- =GIT_EDITOR= :: commit messages

** --committer-date-is-author-date

Replaying a commit constructs a new commit object. Author name, email and date
are copied from the original; committer fields default to the current user at
the current time. This flag overrides the committer date to reuse the author
date. Committer name and email are unaffected.

Without it, a rebased history carries committer dates clustered at the moment of
the rebase, which is the ordinary tell that history was rewritten.

* Hash cascade

A commit SHA hashes the tree, the parents, both identity/date pairs, and the
message. Editing the root changes its SHA, which changes the second commit's
parent pointer, which changes its SHA, and so on.

One edit at the base of a history therefore rewrites every commit above it. A
three-commit branch goes to =ahead 3, behind 3= against its remote.

* Worked example

| commit               | original |  after pass 1 | after pass 2 |
|----------------------+----------+---------------+--------------|
| inital commit        |  5097893 |       e62203e |      4b4d022 |
| Add huggingface data |  c464e12 |       28be6cb |      be5c828 |
| add bibtex for paper |  dda0d4b |       7b56c70 |      31f3e25 |

Pass 1 changed the root's tree. Pass 2 changed the root's committer date. Each
was sufficient on its own to rewrite all three hashes.

* Publishing

#+begin_src sh
git push --force-with-lease=main:dda0d4b origin main
#+end_src

=--force-with-lease= refuses the push if the remote branch has moved since it
was last observed, so a collaborator's commits are rejected rather than
overwritten.

The check compares against the local remote-tracking ref, /not/ the live remote.
=git fetch= updates that ref --- including editor background auto-fetch --- after
which the lease passes and the collaborator's work is clobbered anyway. Pinning
the expected SHA explicitly (=main:<sha>=) closes this, since a pinned value
cannot be advanced by a fetch. =--force-if-includes= (git >= 2.30) is the
alternative.

* Recovery

Tags taken before each pass hold the prior state:

#+begin_src sh
git reset --hard backup-pre-rewrite   # true original
git reset --hard backup-pre-datefix   # rewritten content, pre-date-fix
#+end_src

Superseded commits also remain in the reflog until it expires (90 days by
default). Deleting the tags removes the only durable local anchor.

* Caveats

- Force-pushing does not unpublish anything. GitHub keeps superseded commits
  reachable by SHA, at =/commit/<old-sha>= and through the API, until garbage
  collection --- which for a repository with forks or open pull requests may not
  happen without a support request.
- Existing clones retain the old commits in their reflogs, and a collaborator
  who pushes without resetting will restore them to the remote. Collaborators
  need =git fetch && git reset --hard origin/main=.
- Matching committer dates removes a date inconsistency, not the rewrite itself.
  The published SHAs no longer match what anyone previously fetched, and that
  mismatch is the observable artifact.
